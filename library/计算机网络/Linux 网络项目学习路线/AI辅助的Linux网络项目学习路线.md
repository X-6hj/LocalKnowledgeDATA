# AI 辅助的 Linux 网络项目学习路线

> 适用对象：计算机基础课程尚未系统学习、即将进入大二，希望以计算机网络为主线，同时学习 Linux、操作系统和数据结构，并借助 AI 完成实际项目的学习者。

---

## 1. 路线结论

原计划：

```text
网络诊断工具 → 多人 TCP 聊天室 → Mini HTTP 服务器
```

方向合理，三个项目之间存在清晰的递进关系：

1. **网络诊断工具**：学习如何使用网络协议，观察 DNS、TCP、HTTP 的工作过程；
2. **多人 TCP 聊天室**：自己设计应用层协议，处理并发连接和消息边界；
3. **Mini HTTP 服务器**：实现一个已有标准的应用层协议，综合运用 Linux 网络编程知识。

考虑到目前基础较少，建议增加一个很短的 Socket 热身阶段，并缩小第一个项目的初始范围：

```text
阶段 0：TCP Echo 热身实验
        ↓
阶段 1：分层网络诊断工具 netprobe
        DNS → TCP → HTTP
        ↓
阶段 2：多人 TCP 聊天室
        自定义协议 → 多客户端 → poll/epoll
        ↓
阶段 3：Mini HTTP 服务器
        请求解析 → 静态文件 → 并发处理
        ↓
可选拓展：文件传输、DNS 缓存、HTTP 代理、Mini Shell
```

这条路线不要求预先学完计算机网络和操作系统。学习方式应当是：**先掌握完成当前功能所需的最小知识，再通过运行、抓包、调试和复盘补全理解。**

---

## 2. 学习目标与范围

### 2.1 主要目标

完成路线后，应当能够：

- 熟悉 Linux 下基本的开发、编译和调试流程；
- 理解域名、IP、端口、DNS、TCP、HTTP 之间的关系；
- 使用 Linux Socket API 编写客户端和服务器；
- 理解阻塞、非阻塞、超时和 I/O 多路复用；
- 正确处理 TCP 粘包、拆包、部分发送和连接断开；
- 阅读简单协议文档并将其转化为代码；
- 使用 `gdb`、`strace`、`ss`、`tcpdump`、`curl`、`nc` 定位问题；
- 在 AI 辅助下完成项目，同时保留独立解释和调试代码的能力。

### 2.2 暂不追求的内容

为了保证可行性，前期不加入以下内容：

- Qt 或其他 GUI；
- 用户注册、数据库、复杂权限系统；
- TLS/HTTPS 的完整实现；
- 分布式部署、微服务、容器编排；
- 完整实现所有 HTTP/1.1 特性；
- 一开始就追求高并发和极致性能。

这些功能会显著扩大工作量，却不会提高初学阶段的核心学习收益。

## 3. 技术选型

### 3.1 推荐语言

使用 **C++17 或 C++20**，但网络部分直接使用 Linux POSIX API。

推荐原因：

- 能直接接触 `socket()`、`connect()`、`accept()`、`send()`、`recv()` 等系统调用；
- C++ 的字符串、容器和 RAII 可以降低无关的内存管理负担；
- 后续适合实现缓冲区、线程池、协议消息和状态机；
- 与已有 C/C++ 学习经验容易衔接。

前期不建议直接使用 Boost.Asio、Qt Network、libevent、Crow、Drogon 等框架。完成基础项目后再使用框架重写，才能理解框架帮助处理了哪些问题。

### 3.2 推荐工具

```text
编译器：g++
构建：CMake
版本管理：Git
调试：GDB、AddressSanitizer、UndefinedBehaviorSanitizer
系统观察：strace、ss、lsof
网络测试：curl、nc、dig
抓包：tcpdump 或 Wireshark
```

建议项目目录：

```text
~/projects/computer-network-learning/
├── 00-echo-lab/
├── 01-netprobe/
├── 02-tcp-chat/
├── 03-mini-httpd/
└── notes/
```

如果使用 WSL2，普通 TCP/UDP、线程、`poll` 和 `epoll` 开发基本可行。但 WSL2 使用虚拟网络，Raw Socket、抓包、网卡和路由结果可能与原生 Linux 不完全相同。后期学习底层网络时，可以再使用 Ubuntu 虚拟机或原生 Linux 验证。

## 4. 阶段 0：TCP Echo 热身实验

### 4.1 项目目标

编写一个最简单的 TCP Echo Server 和 Client：客户端发送文本，服务器原样返回。

示例：

```text
Client: hello
Server: hello
```

### 4.2 最小功能

- 服务器绑定 `127.0.0.1:9000`；
- 服务器监听并接受一个客户端连接；
- 客户端连接服务器并发送一行文本；
- 服务器接收后原样返回；
- 双方正常关闭连接；
- 对常见错误输出可读信息。

### 4.3 需要理解的函数

```cpp
socket()
bind()
listen()
accept()
connect()
send()
recv()
close()
```

### 4.4 必须回答的问题

- IP 和端口分别标识什么？
- 监听 Socket 和连接 Socket 为什么不是同一个？
- `accept()` 返回的文件描述符有什么作用？
- Socket 为什么可以像文件一样用整数表示？
- 客户端先退出和服务器先退出分别会发生什么？

### 4.5 完成标准

- 能在两个终端中运行服务器和客户端；
- 能发送并收到至少十条不同消息；
- 服务器未启动时，客户端能正确报告连接失败；
- 能用 `ss -antp` 观察监听和连接状态；
- 能解释客户端和服务器的函数调用顺序。

建议用时：**1～2 天**。如果超过三天仍未完成，应减少代码结构，只保留单连接和纯文本收发。

## 5. 阶段 1：分层网络诊断工具 netprobe

## 5.1 项目定位

第一版不要做成包含 Ping、Traceroute、抓包、测速和扫描的“大而全工具”。建议先实现一个分层连接诊断器：

```bash
./netprobe example.com
```

示例输出：

```text
[DNS ] example.com -> 93.184.216.34     OK      12 ms
[TCP ] 93.184.216.34:80                 OK      25 ms
[HTTP] GET / -> HTTP/1.1 200 OK         OK      43 ms

Conclusion: DNS、TCP 和 HTTP 均正常
```

它的学习重点是回答：

> 当用户输入一个域名并访问网站时，DNS、TCP 和 HTTP 分别做了什么？失败可能发生在哪一层？

## 5.2 MVP 功能

### A. DNS 解析

- 使用 `getaddrinfo()`；
- 输出解析出的 IPv4/IPv6 地址；
- 测量解析耗时；
- 处理域名不存在等错误。

### B. TCP 连接测试

- 指定目标端口；
- 尝试建立 TCP 连接；
- 区分连接成功、连接被拒绝和连接超时；
- 输出建连耗时。

### C. HTTP 请求测试

- 自己构造简单 HTTP 请求；
- 使用 `send()` 和 `recv()` 完成请求；
- 解析响应状态行；
- 第一版只处理明文 HTTP，不实现 TLS。

示例请求：

```http
GET / HTTP/1.0
Host: example.com
Connection: close

```

### D. 统一结果

每层结果至少包含：

```cpp
struct ProbeResult {
    bool success;
    std::string stage;
    std::string message;
    long elapsed_ms;
};
```

## 5.3 推荐开发顺序

1. 解析命令行参数；
2. 完成 DNS 解析；
3. 完成阻塞式 TCP 连接；
4. 增加连接耗时统计；
5. 增加非阻塞连接和超时；
6. 发送 HTTP 请求；
7. 解析 HTTP 状态行；
8. 统一错误信息和最终结论；
9. 补充测试和 README。

## 5.4 必测场景

- 正常域名和开放端口；
- 不存在的域名；
- 正确主机但端口未开放；
- 无法在规定时间内连接的地址；
- 服务器建立连接后立即关闭；
- 返回非 `200` 状态码的网站；
- 用户输入非法端口或缺少参数。

## 5.5 后续拓展

完成 MVP 后可按兴趣选择，不要求全部实现：

- 同时检测多个端口；
- `--json` 结构化输出；
- 并发检测多个主机；
- 使用 `poll()` 处理多个检测任务；
- 统计最小、最大和平均延迟；
- IPv6 支持；
- ICMP Ping；
- Traceroute；
- 通过 Netlink 获取网卡和路由信息。

Ping 和 Traceroute 应放在后期，因为它们会涉及 Raw Socket、ICMP、TTL、校验和及权限问题。

## 5.6 避免低学习价值实现

不应把下面的方式作为核心实现：

```cpp
system("ping example.com");
system("curl example.com");
```

系统命令可以用于对照和验证，但 DNS、TCP 和 HTTP 核心逻辑应使用 Socket API 自己实现。

建议用时：**1～2 周**。

## 6. 阶段 2：多人 TCP 聊天室

## 6.1 项目目标

实现一个命令行多人聊天室：多个客户端连接同一个服务器，服务器负责转发消息。

```text
chat-server
chat-client
```

这个阶段从“使用协议”进入“设计协议”，是整条路线中理解 TCP 最重要的项目。

## 6.2 第一版功能

- 一个服务器支持多个客户端；
- 客户端设置用户名；
- 普通消息广播给所有在线用户；
- 显示用户加入和退出；
- 客户端异常断开不会导致服务器退出；
- 使用一连接一线程的方式先完成功能。

## 6.3 第二版功能

- 在线用户列表；
- 私聊；
- 多聊天室；
- 心跳检测；
- 空闲连接超时；
- 消息长度限制；
- 服务端日志。

## 6.4 必须解决：TCP 消息边界

TCP 是字节流，不会保存消息边界。发送方连续发送 `hello` 和 `world`，接收方可能一次收到 `helloworld`，也可能分多次收到。

因此不能认为：

```text
一次 send() 对应一次 recv()
```

建议使用长度前缀协议：

```text
+----------+----------+----------+----------------+
| 版本 1B  | 类型 1B  | 长度 4B  | 消息内容 N 字节 |
+----------+----------+----------+----------------+
```

至少处理：

- 网络字节序；
- `htonl()` 与 `ntohl()`；
- 接收缓冲区；
- 半包和粘包；
- 部分发送；
- 无效长度；
- 客户端中途断开。

## 6.5 并发模型升级

推荐顺序：

1. 一连接一线程：容易理解，先保证功能正确；
2. `poll()`：理解一个线程管理多个文件描述符；
3. `epoll()`：作为 Linux 专项拓展。

不建议第一天就使用 `epoll`，否则容易同时陷入协议、并发和系统调用三个问题。

## 6.6 可用的数据结构

- 哈希表：用户名到连接的映射；
- 集合：房间成员；
- 队列：待发送消息；
- 动态缓冲区：保存未解析完整的消息；
- 小根堆或时间轮：后期管理连接超时。

## 6.7 完成标准

- 至少五个客户端可以同时聊天；
- 任意客户端断开后服务器继续运行；
- 连续快速发送消息不会出现乱码或消息错位；
- 一条消息被拆成多次发送时仍能正确解析；
- 能说明线程模型和 `poll/epoll` 模型的差异；
- 使用 AddressSanitizer 检查后无明显内存错误。

建议用时：**2～3 周**。

## 7. 阶段 3：Mini HTTP 服务器

## 7.1 项目目标

实现一个可以被浏览器和 `curl` 访问的简易 HTTP 服务器，将前两个项目的知识组合起来。

```bash
curl -v http://127.0.0.1:8080/
```

## 7.2 版本迭代

### V0：固定响应

无论访问什么路径，都返回：

```http
HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 13
Connection: close

Hello, world!
```

### V1：解析请求

解析：

- 请求方法；
- URL 路径；
- HTTP 版本；
- 请求头；
- 请求结束位置。

### V2：静态文件

支持读取并返回：

- HTML；
- CSS；
- JavaScript；
- PNG/JPEG；
- 纯文本文件。

支持基本状态码：

- `200 OK`；
- `400 Bad Request`；
- `404 Not Found`；
- `405 Method Not Allowed`；
- `500 Internal Server Error`。

### V3：并发与稳定性

- 线程池或 `epoll`；
- 请求读取超时；
- 限制请求头大小；
- 输出缓冲区；
- 访问日志；
- 可选 Keep-Alive。

## 7.3 必须考虑的安全问题

至少处理：

- 拒绝 `../../etc/passwd` 等路径穿越；
- 限制请求行和请求头长度；
- 处理畸形请求；
- 不允许无限等待；
- 拒绝不支持的方法；
- 文件路径必须限制在指定网站根目录内。

## 7.4 测试方法

```bash
curl -v http://127.0.0.1:8080/
curl -v http://127.0.0.1:8080/not-found
nc 127.0.0.1 8080
```

后期可以使用：

```bash
ab -n 1000 -c 20 http://127.0.0.1:8080/
```

性能数字不是第一目标，先确保并发下响应正确、程序不崩溃、文件描述符能够释放。

## 7.5 完成标准

- 浏览器和 `curl` 都能正常访问；
- 可以正确返回静态文件；
- 至少支持五种基本状态码；
- 畸形请求不会让服务器崩溃；
- 多客户端并发访问时结果正确；
- 能用抓包解释一次 HTTP 请求与响应；
- 能说明 HTTP 与聊天室自定义协议的共同点和区别。

建议用时：**2～4 周**。

## 8. 可选拓展项目

完成主线后，只选择一个拓展即可。

### 8.1 TCP 文件传输工具

学习：文件 I/O、分块传输、进度统计、断点续传、哈希校验、背压。

### 8.2 Mini DNS 查询器或缓存服务器

学习：UDP、二进制协议、位字段、TTL、哈希表、LRU 缓存。

### 8.3 HTTP 代理服务器

学习：双向转发、连接管理、缓存、黑名单、流量统计。

### 8.4 Linux Mini Shell

学习：`fork()`、`exec()`、`waitpid()`、管道、重定向、信号、前后台进程。

### 8.5 简单抓包和协议分析器

学习：以太网帧、IPv4、ICMP、TCP、UDP 和网络字节序。该项目对权限和运行环境要求更高，应放在主线之后。

## 9. 与计算机四大件的联系

通常所说的计算机四大件包括数据结构与算法、操作系统、计算机网络和计算机组成原理。

| 项目 | 计算机网络 | 操作系统 | 数据结构 | 组成原理 |
|---|---|---|---|---|
| Echo 实验 | TCP、端口 | 系统调用、文件描述符 | 缓冲区 | 字节与内存 |
| netprobe | DNS、TCP、HTTP | 非阻塞 I/O、超时 | 结果集合、统计 | 大小端、系统调用开销 |
| TCP 聊天室 | 应用层协议、长连接 | 线程、poll、epoll | 哈希表、队列、状态机 | 字节序、上下文切换 |
| HTTP 服务器 | HTTP、连接管理 | 文件 I/O、线程池、epoll | 缓冲区、任务队列 | 用户态与内核态、缓存 |

这条路线不会完整覆盖四门课程，但会建立课程之间的联系。以后课堂上学习相关概念时，可以回到项目中寻找实际对应位置。

## 11. AI 辅助开发规则

AI 应当扮演教师、代码审查者和调试助手，而不是一次性代码生成器。

### 11.1 每个功能的推荐流程

1. 自己先写一句功能目标；
2. 让 AI 解释涉及的概念和设计选择；
3. 自己写接口、数据结构或伪代码；
4. 让 AI 只实现一个小模块；
5. 编译并实际运行；
6. 根据真实错误与 AI 一起调试；
7. 为成功和失败场景补测试；
8. 用自己的语言记录实现原理。

### 11.2 适合向 AI 提的问题

```text
请先解释，不要写代码：非阻塞 connect 为什么返回 EINPROGRESS？
```

```text
请检查这个 recv 循环是否能处理半包和客户端断开，只指出问题和修改方向。
```

```text
请为这个 HTTP 请求解析器设计 10 个失败测试，不要修改实现。
```

```text
下面是 strace/tcpdump 的真实输出，请结合输出定位问题，不要猜测程序已成功。
```

### 11.3 不推荐的方式

```text
请一次性生成一个高性能、支持 epoll、线程池、HTTPS、数据库和 GUI 的完整服务器。
```

这样得到的代码通常超过当前理解范围，也难以验证正确性。

### 11.4 每次使用 AI 后自检

至少回答：

- 这段代码解决了什么问题？
- 为什么使用这个系统调用？
- 失败时返回什么？
- 资源在哪里关闭？
- 是否处理部分发送和部分接收？
- 我能否独立修改一个小功能？

如果无法回答，就暂时不要继续增加新功能。

## 12. 测试与验收方法

每个项目都需要四类验证：

### 12.1 正常测试

确认基本功能能运行，而不是只编译成功。

### 12.2 失败测试

主动测试错误域名、错误端口、断开连接、非法消息和畸形请求。

### 12.3 系统观察

```bash
ss -antp
strace -f ./program
tcpdump -i any port 8080
```

将代码行为和 Linux 内核暴露出来的状态联系起来。

### 12.4 内存与资源检查

编译阶段开启：

```text
-Wall -Wextra -Wpedantic
-fsanitize=address,undefined
```

同时检查：

- 文件描述符是否关闭；
- 线程是否能正常退出；
- 异常路径是否释放资源；
- 输入长度是否有限制；
- 服务器长时间运行后是否仍然稳定。

## 14. 风险与控制方法

| 风险 | 表现 | 控制方法 |
|---|---|---|
| 项目范围膨胀 | 不断加入 GUI、登录、数据库 | 每阶段只做 MVP，拓展写入待办 |
| AI 代替学习 | 代码能运行但无法解释 | 每次只生成一个模块并完成复盘 |
| 过早优化 | 功能未正确就开始 epoll | 先阻塞，再线程，最后 I/O 多路复用 |
| 只测成功情况 | 换个输入程序就崩溃 | 为每个功能设计失败测试 |
| 卡在环境问题 | WSL 抓包或 Raw Socket 异常 | 先完成普通 TCP，底层部分用 Ubuntu VM 验证 |
| 理论和代码脱节 | 会背概念但不会定位代码 | 用 strace、ss、tcpdump 观察真实行为 |
| 项目中途放弃 | 第一版目标过大 | 保证每周都有可运行的小版本 |

## 15. 最终评价

“网络诊断工具 → 多人 TCP 聊天室 → Mini HTTP 服务器”是一条合理、可行并且具有拓展性的路线。它适合当前阶段的前提是：

1. 在正式项目之前完成一个很小的 Echo 实验；
2. 把网络诊断工具第一版限制为 DNS、TCP 和 HTTP 三层诊断；
3. 聊天室先使用简单线程模型，再学习 `poll/epoll`；
4. HTTP 服务器只实现必要的 HTTP 子集；
5. 每个阶段都必须运行、测试、观察和复盘；
6. AI 每次只辅助一个可验证的小任务。

最推荐的起点不是阅读大量理论，也不是让 AI 直接生成整个项目，而是先完成：

```text
TCP Echo Server + Client
```

完成后再正式创建 `netprobe`。这样既不会因为基础不足而无法开始，也能让后面的网络诊断、聊天室和 HTTP 服务器形成连续、可复用的知识链。
